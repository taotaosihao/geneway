## 1. 总目标、全量范围与工作位置

### 1.1 全量重建的定义

全新建设基于 DeepSeek Harness（DSH）原生运行和插件机制的制造业数字员工产品。管理员在后台定义数字员工（Agent）及其开放范围；企业每名成员可以在自己完全隔离的会话中使用获准 Agent，并自助接入自己的飞书或微信。用户可以配置员工与能力、委托真实工作、持续跟进、组织协作、使用私有和共享知识、通过多个渠道交互、配置定时或事件任务，并在明确授权下完成有限业务写入。

“完全重建”表示不依赖旧 Geneway 的代码、服务、数据库、会话、令牌、插件协议或验收流程；“全量交付”表示本合同全部目标和必达阶段完成。第一项查询、一个插件探针或原最小版本通过，都不能作为全量项目结束条件。

保留原三个目标的含义，并增加全量能力目标：

| 目标 | 全量交付义务 | 主要阶段 |
|---|---|---|
| G1 真实工作 | 普通业务入口中的员工调用已授权真实来源，结构化结果、业务说明和来源一致，可追问；不以合成响应冒充接入。 | P1，v4.4 起由 P4-K0 以 Kivo 重新验证，后续持续保持 |

| G4 动态协作与任务推进 | 多名员工在同一任务下按需分工、交接、复核与汇总；可展示和调整工作计划，不固定专家角色、顺序或轮数。 | P3 |

### 1.2 有边界的全量产品

最终交付按单企业独立部署定义，支持多个人类成员和多名数字员工；最初 P1 可以先由一个授权操作者验证。数字员工数量、用户数量、并发容量和模型预算由阶段计划给出可测目标，不宣称无限规模。

Web 为完整工作台与配置入口，并提供移动端关键操作适配。飞书和微信承担约定的消息交办与反馈，不要求复制所有 Web 管理页面。微信形态已由用户决定（2026-10-15）：每名成员的个人微信经腾讯官方 iLink「微信机器人」协议接入，由 Geneway 内置微信通道并复用 dsh-im 的 iLink 协议与扫码实现（见 §5.4）；企业微信、微信客服不在当前必达范围，也不能静默替代已选形态。成员微信账号不具备「微信机器人」入口或接口不可用时，该成员的微信接入如实显示不可用。飞书与微信的验收按用户决定采用模拟验收（见 §5.4），只发链接或单向通知不算接入完成。

协作、知识、多渠道、主动工作、有限业务写入和可运维交付均是必达范围，不再写成“以后可能增加”。“全量”不表示支持所有 ERP/MES、全部制造业务或任意第三方代码。

不纳入：旧系统迁移或兼容、重建 MES/ERP/FMS 核心业务、共享进程多租户 SaaS、外部 Agent 联邦、插件市场及不可信 Host 代码执行、通用可视化 Workflow/DSL 平台、事务性热升级、未经独立授权的 PLC/机器人/机床动作。知识产品能力与最小任务触发必须实现，但不因此另造通用记忆引擎或 Agent 调度框架。

## 2. 强制工程流程：每个大阶段先由 planner team 详细规划

### 2.1 不可省略的顺序

**对 P1–P7 每个大阶段，必须先完成该阶段的真实 planner team 详细规划，再开始该阶段实施。总合同、阶段大纲、前一阶段计划或一次全项目规划，都不能替代本阶段详细计划。禁止边实施边补计划，禁止先写完再补签。P7 即使以集成验证为主，也适用。**

执行顺序为：当前事实与依赖发现 → planner team 独立规划与讨论 → 主代理形成该阶段唯一详细计划 → 检查计划就绪及实施权限 → 实施计划中的就绪任务 → 阶段验证与交接 → 下一阶段重新规划。

本规则是用户要求的开发前置，不是产品中每次聊天、查询或数字员工工作都要经过规划委员会。

### 2.2 planner team 的真实参与要求

每阶段由主代理汇总，至少两名实际运行的独立 planner 子代理参与。默认分别侧重“产品结果与当前交付”和“工程集成与验证边界”；视角可以按阶段调整，不建设永久角色目录或协调服务。

两名 planner 收到同一份当前合同、阶段目标、前序实际产物、有效决定、已有证据和权限限制，先独立形成完整阶段意见，再交换会改变方案的实质分歧。主代理依据事实选定方案，不机械拼接所有建议，也不要求为一致而无限讨论。

两名 planner 收敛后、阶段计划批准实施前，再由一名未参与该阶段规划和实现的独立过度设计审查者检查：是否新增了没有当前合同义务的对象、服务、依赖、抽象、状态、配置或证据包装；是否已经存在更小的标准库、平台原生或仓库既有路径。审查者不承担正确性评审，不能通过删减功能、安全、权限、恢复、数据完整性或用户明确要求来换取更少代码。

对有实质争议的复杂度，审查者做有界消融：只比较当前方案与一个或少数最小删减/合并变体，使用现有合同、调用点、确定性测试或有限只读/本地实验判断删减后是否仍完整满足目标。能满足的选最简变体；不能满足的记录失败证据并保留当前边界。不得把消融扩成全项目重写、性能竞赛或为了证明规则而移除真实安全门。

主代理在阶段计划内简要记录两名 planner 和独立过度设计审查者的标识、视角、返回结果引用、读取限制、采纳与未采纳的关键取舍，以及争议复杂度的消融变体、证据与裁决。只有角色名称、主代理模拟多种意见、复制旧评审、只有一个有效 planner 返回，或过度设计审查者参与了同阶段方案创作/实现，均不满足团队规划。子代理依赖主代理提供的原文可以参与，但不得声称独立读过源码或运行过测试；关键环境事实仍须由获准且有能力的一方核实。

使用当前可用且获准的子代理通道，不擅自改模型提供商、主会话或全局配置。通道不能启动、返回无有效内容或不足两份独立规划意见时，该阶段保持规划未就绪；可以继续获准的只读发现和文档整理，不能静默降级为单人实施。改变此要求必须有用户明确决定。

### 2.3 详细计划必须包含什么

每阶段只维护一份有效计划，路径为本合同目录下 `phase-plans/P1-plan.md` 至 `phase-plans/P7-plan.md`。已存在的阶段计划按其记录的结论有效；尚未开始的阶段不预建空文件，不声明已经规划。阶段范围因合同修订而扩大时，在原计划文件内原位重规划受影响部分，不另建平行计划。

| 必备内容 | 必须达到的粒度 |
|---|---|
| 阶段目标与覆盖 | 对应 G、J、AC 的具体行为；本阶段交付与非目标；不得删除全量义务。 |
| 当前事实与前序结果 | 当前代码基线、实际存在的入口/接口/存储、前序验证结论和未完成依赖；区分已观察事实与假设。P1 同时按 §11 提前识别后续必达外部条件，后续阶段更新相关事实。 |

| 最简方案与有界消融 | 独立过度设计审查者、可删除/合并的候选复杂度、最小变体、合同/调用点/测试证据和保留或删除裁决；不能以简化为由降低功能、安全、权限、恢复或数据完整性。 |

### 2.4 规划之前、规划之后的动作边界

计划前可以在已有权限下阅读合同、当前源码、依赖声明、已有测试/日志与官方资料，以及检查 Git、目录和已有安装产物元信息。资料发现不自动授权读取凭据、客户数据或其他仓库。

安装依赖、执行安装脚本、编写或运行代码探针、启动应用、调用产品模型或真实接口均属于实施或外部运行，不得以“只做探针”“临时目录”“先跑一下”为例外跳过阶段规划。planner 自身用于本次规划的模型推理，不等于调用待建产品模型或业务系统。

P1 详细计划，以及因底座升级或新外部通道而重规划的阶段计划（如 v4.3 的 P4），可以把相容包集安装/升级和原生接口探针列为第一个实施任务，无需在计划前先证明它们运行成功。该任务须先有问题、有限执行范围、验证方法及失败分支。阶段计划中已明确接受的有限分支，由主代理根据探针证据选择；超出分支或改变责任/行为时先重规划受影响部分。

### 2.5 何时可以开始实施

开始某阶段任务前，同时满足：本阶段完整计划已由真实 planner team 形成；独立过度设计审查与必要的有界消融已完成；计划覆盖全部本阶段义务且影响实施的分歧已解决；当前任务的前序产物、数据与权限满足；用户实施授权覆盖当前阶段及动作。

某个真实来源、渠道账号或写入权限未具备，可以在完整计划中列为该任务的阻塞，实施不依赖它的已就绪任务；不得把受阻义务删掉、把未完成阶段标成完成，或提前实施尚无详细计划的下一阶段。关键方案仍不明确时只能继续规划，不能用“外部依赖待定”掩盖缺失的阶段设计。

用户明确要求完整实施本合同时，该授权可持续覆盖 P1–P7 内部工程推进，不必每阶段重复询问同一个授权；产品方面需要决定的事项先由多 agent 探讨通用方案，用户负责阶段最终验收并随时提出问题；但逐阶段团队规划仍不可省略。改变业务目标、渠道形态、共享范围、真实写动作、跨仓库范围或生产部署等用户拥有的决定，必须取得相应明确决定。阶段计划就绪不等于这些外部权限已经取得。

### 2.6 重规划与连续推进

普通文件布局、等价实现或已有任务内的缺陷修复，不要求重开全阶段。实际接口否定关键前提、共享或取消语义改变、新增写入风险、验收方法失效时，暂停受影响工作，由至少两名实际 planner 对变更部分复核，主代理原位更新当前计划及下游影响；无关任务可按原计划继续。

默认采用第 9 节顺序。可以提前做后续阶段的只读发现与草案，但进入该阶段前必须依据前序实际结果更新并完成其团队规划。重排或拆分必须保留目标、验收映射及新的依赖依据；不能通过合并全项目为一个阶段绕过逐阶段规划。

每阶段完成后记录实际入口、验证与未完成项，供下一阶段使用。只保留一份阶段计划和一份必要的验证记录，允许复用现有合适载体；不生成 authority/admission/receipt 文件链，不为本规则开发通用审批平台。

## 3. 架构与产品对象的职责

### 3.1 DSH 与 Geneway

DSH 是实际执行底座，使用原生 Profile、Bundle、插件、Agent、Session 和所选协作能力；具体包集及 API 由相应阶段规划后在真实安装产物中验证，不默认继承旧版本，也不以文档描述代替运行证据。

DSH 版本政策（v4.3）：用户决定 DSH 更新到最新。“最新”指 npm `@deepseek-ai/dsh` 的 `latest` 标签在升级任务开始时指向的版本，2026-10-15 为 `0.2.0-rc.2`；`alpha` 标签不作为默认目标。用户在本轮实施中确认按官方发行体系锁定：DSH 主包与同发行列车的 `@deepseek-ai/dsh-*` 配套依赖及 peers 统一精确锁定到同一版本；独立发版的 Cordis、Cordis 插件和 Schemastery 按该 DSH 版本声明的相容范围解析，并在 lockfile 固定实际版本，项目直接依赖和 override 使用精确版本（本次 `cordis-plugin-group` 为 `1.0.4`），不得忽略 peer mismatch。不对 DSH 配套包单独取各自的 `latest` 标签。升级须：先备份产品存储与 DSH home；比对新版本默认生效的插件/工具清单与 Geneway 禁用清单，出现未知或新增可用能力按失败处理直到明确裁决；证明升级前的 Session 历史仍可按 §4.3 读取或明确标示不可用；重跑受 Session 格式、插件装配、执行、委派与恢复影响的已通过旅程及已提交的 P6 代码测试；依赖业务来源的部分（J1、J4、J6 的业务部分，J8 事件，J9）不在 GearJob 上重跑，由 P4-K0、P5-K1 在升级后的候选上以 Kivo 验证。不以“版本更新”跳过回归或静默降级为旧版本；升级导致的已提交代码修复归入升级任务。

Geneway 管理人类成员、数字员工、连接与技能绑定、必要工作和协作归属、知识范围、渠道关联、触发规则及业务动作记录。它通过原生服务和事件与底座交互，不复制 AgentLoop、模型 token 状态、工具步骤解释器或会话恢复调度。

Web、渠道和触发适配器使用一致的工作受理、继续、取消与结果查询语义；需要明确返回结果的操作走明确产品服务入口，通知、观察和所需拦截使用原生事件，不靠全局广播的隐含监听顺序决定业务成功。P1 落定最小入口，P4/P5 复用并验证真实装配；原生回调、Session 或 Team 的存在不单独证明业务去重、工作完成或长期员工归属。这里是现有产品职责的落位，不新增通用消息协议、网关或执行解释器。

默认从少部署单元和一种产品事实存储起步。原生扩展存储不足时可以采用嵌入式存储；后续多用户、触发持久性或故障恢复确有证据要求时，可在阶段计划中选用必要成熟组件。既不预设多个网关/Worker/队列，也不把“永远只能一个进程或一种嵌入式库”写成产品约束。每次增加组件必须有当前职责和维护成本依据。

### 3.2 最小稳定关系

| 对象 | 唯一主责及必要关联 |
|---|---|
| 人类成员 | 产品身份与访问范围，管理员维护连接/员工配置，普通成员仅操作获准工作和知识；不是外部渠道昵称。 |
| 数字员工（Agent） | 由管理员在后台定义：稳定员工标识、名称、职责与指令、模型配置引用、技能、工具与连接绑定；不是永久进程或单条 Session。Geneway 产品存储是 Agent 定义的唯一事实源，不在 DSH Agent Preset 或渠道配置中另存可编辑副本。开放成员范围就是既有的“成员可用员工”授权关系（P2 的成员员工授权），后台可从 Agent 侧编辑，但不另存 Agent 侧副本。 |
| 成员会话 | 归属唯一成员和唯一 Agent 的对话线索，承载即时问答并关联其 DSH Session 谱系（因撤销等原因用干净上下文承接时形成后继 Session）。在会话中发起的工作仍是独立对象，保留各自的执行 Session 与 §4.2 取消作用域，只关联到所在会话；停止一项工作不影响同一会话中的其他工作。分为 Web 会话（成员可随时新建多个）和渠道会话（来源为渠道的成员会话，不另建对象类型）。 |
| 渠道身份 | 外部平台账号与产品成员的绑定：飞书为企业应用下经关联码绑定的成员身份；微信为该成员本人扫码得到的 iLink 微信机器人账号，扫码后在 Web 由本人确认脱敏标识，只受理该账号主人发来的消息。一个渠道身份只属于一名成员，绑定、解绑与失效由成员本人或管理员操作。 |
| 插件 | 一份可复用代码能力与原生贡献，由可信维护者部署；安装不等于向所有员工授权。 |
| 连接实例 | 稳定目标身份、插件类型、配置、凭据引用与启用状态；同插件可有多实例。 |
| 工作与协作 | 目标、发起主体、负责员工、业务对象、待补充信息、必要分工/交接及结果关联；即时问答不强制创建工作。 |
| Session 与执行 | DSH 拥有运行历史；产品只保存归属关联与必要投影。每次执行只有一个实际执行员工，及零个或一个所属工作。 |
| 知识与确认信息 | 来源、拥有者、可见范围、有效性与更新/撤销依据；共享是明确授权，不是默认复制会话。 |
| 消息、触发与动作 | 保存外部消息映射、规则及发生标识、动作意图与回执等必要业务事实；不成为第二套模型执行框架。 |

一个工作可以关联多次执行和多个有明确归属的协作子工作。员工可参与不同任务，某次委派关系不建立永久上下级。小纬可作为统一入口和默认对外发言者，但不是所有权限、连接与私有记忆的共同拥有者。

Session 不跨员工复用，也不跨成员复用；协作通过明确的任务交接和结果引用交换信息，不合并所有员工的完整上下文。

成员间会话完全隔离：成员会话、对应 DSH Session 历史、附件、确认信息、渠道消息和投递记录只属于该成员。任何其他成员都不能通过 Web、API、渠道命令、会话列表、搜索、导出或 Session 标识读取、绑定、继续或停止该成员的会话，管理员同样不能读取正文。隔离由服务端持有的会话/Session 引用与成员归属校验保证，不靠前端隐藏，也不为隔离给每名成员单独运行 DSH Host 或进程；只有当选定装配向模型开放文件、命令或附件写入能力时，才要求工作目录与临时文件按成员划分。

管理员默认不能读取成员会话与工作正文（用户 2026-10-15 决定，延续 P2 已验收行为），只见用量、耗时、错误码、渠道连接状态等运维所需元数据；排查需要正文时，由成员把指定会话或工作结果主动分享给管理员。离职交接、合规或安全事件的受控调阅（理由、不可删除记录、通知被查看成员）列为后续可选项，需用户另行决定，不属于当前必达范围。隔离约束的是产品角色与产品入口；主机运维和备份持有者按部署访问控制管理，不做每成员加密或新建审计平台。

允许的跨成员信息流只有：§5.3 明确授权的共享知识、成员明确共享给指定成员的工作结果，以及经 §5.4 接收范围检查的群聊输出。Agent 的私有知识与记忆按“成员 × Agent”划分，同一 Agent 开放给多名成员时，一名成员会话中的内容不得经该 Agent 的私有范围被另一名成员检索或注入。不得经由共享工作目录、共享渠道机器人或会话绑定隐式流动。工作负责人、实际执行员工、工具连接和结果归属在派发前明确，回传时不能读取可变的全局“当前工作/当前连接”决定归属。

### 3.3 插件、Connector、Tool、Skill

大部分业务、渠道、知识来源、触发及专用工具以 DSH 原生插件组合；插件边界依据独立变化、替换或资源生命周期，不以插件数量为目标。技术上以插件装配，不等于产品上可由普通用户随意关闭。

| 能力类别 | 依赖与缺失时的行为 |
|---|---|
| DSH 必需运行能力 | 实际执行、Session、所需持久化与传输优先复用原生实现；缺失时依赖它的路径明确不可用，不另写替代运行框架。 |
| Geneway 必需公共能力 | 身份、授权、员工绑定、工作及结果归属必须有有效提供者；可以也是原生产品插件，缺失不能进入免检查执行模式。 |
| 可选装配能力 | 具体 Connector、渠道、知识来源、触发适配和计算工具按依赖装配；未安装或停用只使它及明确依赖它的能力不可用，不自动换绑，不拖垮无关入口。 |

“可选装配”只表示运行依赖可分离，不降低 G1–G9 的全量实现与验收义务。共同产品职责不反向依赖某个具体业务或渠道实现。对应能力形成时验证最小装配，例如不装飞书仍可使用 Web，未装知识能力仍可进行普通聊天和已配置业务读取；不要求穷举插件组合，也不要求移除必需授权能力后业务继续执行。

业务插件可同时包含 HTTP 客户端、规范化、确定性函数、工具与可选展示；不要求每个插件实现 runtime/connector/web/executor 四个面。纯工具插件可直接使用通用结果展示。注册、依赖和资源清理由原生机制管理，不新增 Geneway install/activate/dispose 协议。

Connector 提供真实访问，Tool 是可调用动作，Skill 提供任务方法；它们不是三套必须独立部署的服务。外部业务系统以 MCP 服务提供工具时（如 §5.6 的 Kivo），Geneway 业务插件作为 MCP 客户端访问它，再按员工绑定、连接和当前授权把允许的工具以 DSH 工具暴露；不把外部 MCP 服务直接挂给 DSH 模型而绕过 Geneway 的授权、批准和结果记录；可暴露的工具以插件内固定的允许清单为准（§5.6）。状态映射、单位转换、数量计算、权限检查和稳定 API 聚合由程序实现，模型选择能力、提问、分工和解释。

用户可以选择和配置技能、查看启用状态及其依赖能力。技能建议不能扩张权限。普通业务新增主要修改自身插件、技能、绑定及必要产品接口，不改 AgentLoop、会话调度或恢复协议；确有新产品概念允许增加小接口，不追求绝对零共享修改。

## 4. 执行、授权、取消与结果

### 4.1 每次实际派发的范围

服务端解析当前成员或规则授权主体、员工、工作、渠道/触发来源、连接、动作和对象范围。客户端、模型提交的用户/连接/对象标识仅是选择参数，不构成授权；不接收模型任意提供的目标 URL 或凭据。

每次业务派发及新增重试都检查当前绑定、启用状态、动作范围和上游权限，包括工具适配器内部重试。无法经过检查的自动重试关闭或纳入同一窄调用入口；不另造通用重试平台。UI、模型工具、子任务、渠道和定时触发调用均使用同一有效政策，纯计算工具也检查员工是否绑定该能力。

委派和知识共享不合并参与者权限。协作执行同时受工作发起者的授权范围和执行员工绑定约束；只交接完成任务需要且接收方获准的信息。调度规则保存明确授权主体，但不能让其历史身份成为永久通行证。账号、规则、连接或绑定禁用后不得继续新派发。

变更连接的目标业务实例时创建新连接标识；同目标凭据轮换可以保留身份，后续派发读取当前有效引用。原连接失效时，不静默切换到另一实例查询同名工单；换目标须明确选择并记录。

### 4.2 工作级停止与重复提交

停止某项工作不得取消另一项已接受工作。不同独立工作不得同时进入同一原生取消作用域；可使用具有独立取消范围的 Agent/Session，或忙碌时明确不接受第二项执行并保留待办。只有 Session 标识不同不算取消隔离，不强制建立并行队列。

同一工作当前已有已接受且尚未结束的执行时，重复继续只返回该执行状态，不重复启动或额外派发；已结束的历史执行不阻止补充后产生新的关联执行。

工作停止、停止该工作明确归属的未完成子工作、停用后续触发规则、撤销待执行动作许可是不同操作。产品必须说明各按钮的作用范围；停止本次执行不隐含删除定时规则，停规则也不伪称撤回已发外部请求。P3/P5/P6 的阶段计划分别将协作、触发和动作场景接入这一规则。

取消或撤销后阻止后续受控派发，在途请求传递所支持的取消并按真实状态说明。原生取消已舍弃的临时响应不要求旁路抢救；已结算且持久化的历史结果保留。HTTP 客户端曾收到响应、模型流结束或 DSH idle 都不单独证明工作成功。

### 4.3 历史、持久化和恢复

当前业务事实以上游本次授权读取为准；当次必要观察及来源保留原来的时间含义，最新查询产生新观察，不覆盖旧卡片。源时间缺失应注明，不能以查询时间冒充采集时间；没有计划基线，不制造提前/落后结论。

需保留的结果保存足以确定当时含义的必要事实、单位、来源、判定依据及实际需要的类型或版本标识。插件升级或替换不得静默用新映射重新解释旧结果；专用展示不可用时，仍可在当前权限下读取已保留的必要事实，无法解释的部分明确标示。优先投影到原生持久结果，自解释字段不机械增加版本体系；不建立全业务 schema 平台，也不恢复旧 Geneway 数据兼容。

插件停用或卸载阻止依赖该能力的新业务派发；运行资源清理不隐含删除需保留的持久数据，也不解除其访问控制、共享撤销与删除义务。插件产生的数据和派生材料必须有明确维护责任，履行这些义务不得以重新开放该插件的业务执行为前提。产品公共能力或受限维护路径负责落实；专属清理暂不可用时，先阻止无权或失效内容被检索、注入、读取或外发，并明确待处理项，不能把停止访问冒充物理删除完成。此规则与 §4.2 的在途边界共同生效，不新增第二套插件生命周期或治理平台。

业务函数形成唯一的结构化判定，模型和 UI 消费同一结果。优先原生持久结果及稳定引用；验证实际持久字段与真实展示消费路径，不只保存“查询完成”而依赖执行期临时值。

仅当原生投影、寻址与简单映射确实不足时，才允许在唯一产品存储保留最小不可变业务观察及来源、时间和原生执行关联；不预建镜像、双写或同步服务。该观察不参与执行调度、旧调用重放，也不能代替要求恢复的 DSH 历史。

只有任务条件满足、必要结果已持久化且可读取，才显示完成。原本未完成的执行恢复后可显示中断；已完成但历史丢失，应显示“历史结果不可用/恢复不完整”，不改写成当时未完成。已有原生持久结果可读取补齐关联；未知外部效果不得自动重放。

基础备份从首批需保留的数据出现时建立；随阶段扩展覆盖身份、绑定、工作与协作、知识有效性、渠道映射、触发发生及动作回执的必要记录和相关 DSH 历史。恢复字符串不等于恢复权限或连接；凭据、账号和外部授权失效时明确不可用。完整升级回退和组合恢复在 P7 验证，不延后基础数据保护。

## 5. 全量产品能力约定

### 5.1 工作连续性与产品管理

工作台提供成员登录与会话归属、员工选择、职责/模型/技能/连接配置、工作发起、反馈、来源、待办、补充、继续和停止。初期固定配置可以推进真实链路，但最终必要配置操作必须有授权产品入口，不能只能手改数据库。

管理员后台提供 Agent 的新建、编辑、停用和开放成员范围配置；成员不能修改 Agent 定义。Agent 的名称、指令等定义编辑只影响之后新开始的执行，不打断正在进行的执行，也不改变既有结果归属；Agent 停用、成员被移出开放范围或连接撤销，则按 §4.1 在后续工具 I/O 与新派发前拒绝，该成员不能再用它新建会话或继续派发，历史会话按当前访问规则只读。调整开放范围不应仅因此强制成员重新登录，授权以每次请求时的当前状态为准；取消现有“变更即递增登录会话版本”的做法之前，派发、批准和动作执行的复核必须已覆盖开放范围与 Agent 停用，不得削弱移出范围后旧批准失效的保护。

成员在 Web 中只看到自己的会话列表，可随时选择获准 Agent 新建会话、重命名或归档自己的会话；渠道会话也出现在同一列表中并可在 Web 继续。新建会话得到新的 DSH Session 和干净上下文，确认信息与获准知识按 §5.3 规则注入，不复制其他会话的历史。

缺少工单标识等条件时，先保留必要待补充工作，再显示继续入口。等待不持续推理、不轮询催办。刷新和正常重启后可找到同一工作；多个候选需要明确选择，不按“最近一条”或含糊文本换工作、换工单。

Web 的确认信息管理、继续、取消、连接测试与禁用须真实可操作。普通连接超时、未配置和可捕获错误局部反馈，不能让无关聊天一并失效；不承诺同进程恶意代码、死循环或内存耗尽的强隔离。

### 5.2 动态协作与工作计划

支持用户指定员工或由负责人按任务需要选择协作者；至少一条真实工作由两名不同员工分工完成，存在可观察的交接、必要补充/复核和结果汇总，而非 UI 展示两个头像或用户手工转发消息。

用户可查看工作目标、参与者、子任务摘要、待补充项、最终结果及其依据，可调整尚未执行的目标或停止相关工作。复杂工作可形成任务级计划并按新事实修订；简单工作直接完成，不强制委员会，不以所有专家一致同意作为普通回答门槛。

原生委派、任务、会话等经验证能力优先；产品保存必要分工和归属，不能借动态工作计划新写通用 Workflow DSL 或执行解释器。确定性的业务工具内部允许固定步骤。协作深度、模型预算、失败时返回部分依据或请求人工介入的规则由 P3 详细规划，不能无限递归。

### 5.3 长期、私有与共享知识

区分用户明确确认的信息和经授权导入的知识材料。前者保存确认依据，后者保存来源和导入权限，不要求逐句人工确认；普通聊天或模型推断不能自动变成已确认事实或企业知识。

至少支持一种真实可用的文档/文本知识导入、更新、检索与引用。产品提供员工私有范围（按成员 × 员工划分，见 §3.2）、用户与员工之间的确认信息范围，以及明确指定成员/员工可访问的共享范围；不要求适配所有文件格式或建设通用记忆平台。

可查看、修正、删除和撤销共享；后续检索和上下文装配排除无权或失效内容，并覆盖仍可召回它的摘要、缓存和协作材料。知识插件停用后仍按 §4.3 履行这些数据义务，不以重新启用检索或业务工具为条件。原生 Session 会隐式携带已撤销内容时，用干净上下文承接同一工作，保留获准的历史关联，不复制整段旧会话重新注入。

历史显示也遵守当前访问范围和既定保留规则，不能把“保留历史”解释成失权成员仍可读取私密内容。不承诺撤回已经发送给外部模型或渠道的数据；用户以后主动重新提供相同信息是新输入。删除效果按实际检索/上下文检查，不以模型偶然使用相同文风判失败。动态生产事实仍重新查源，不当长期知识固化。

### 5.4 Web、飞书与微信通道

三类入口均为必达能力。渠道形态已由用户决定（2026-10-15）：

| 渠道 | 接入形态 | 成员自助接入 |
|---|---|---|
| 飞书 | 企业一个 Geneway 产品飞书应用（机器人），成员私聊该机器人；群聊仅在 @ 机器人且接收范围检查通过时响应。 | 成员在 Web「我的渠道」生成一次性关联码，在飞书私聊机器人发送后完成绑定；不要求每名成员各建一个飞书应用。 |
| 微信 | 成员自己的个人微信，经腾讯官方 iLink「微信机器人」协议长轮询收发，无需公网回调；当前只承诺私聊文本。 | 成员在 Web「我的渠道」发起扫码，用自己的微信扫码后得到只属于该成员的微信机器人账号，并在 Web 确认脱敏标识；账号不具备「微信机器人」入口时明确提示不可用。 |

渠道实现（用户 2026-10-15 在多方审查后决定）：

- 飞书保留 P4 已实现并经真实验证的官方 SDK 运行时，不迁移。同一飞书应用同一时刻只能有一个事件消费者，不与其他系统并行连接同一应用。
- 微信由 Geneway 内置微信通道实现，与现有飞书通道同构，不运行 dsh-im Host，也不经 DSH Host 转发。iLink 协议调用、扫码登录、长轮询、分段与重连复用 dsh-im（npm `@xmanrui/dsh-im`，MIT）的实现：按文件引入并在仓库内记录来源版本、许可与改动；后续同步上游修复由阶段计划安排。复用的是协议层，身份、Agent、会话、工作、授权与投递事实只由 Geneway 维护，dsh-im 自带的会话映射、工作区、Agent Preset、模型切换和 `/session`、`/sessions`、`/workspace` 等命令不进入 Geneway。
- 微信入站须先持久受理再推进长轮询游标，不能在受理完成前确认；无法处理的消息有明确处置，不阻塞后续消息。只受理该账号主人发来的私聊文本；附件和非文本消息明确回复不支持。同一微信账号同一时刻只能有一个长轮询实例。
- 扫码绑定、连接状态与解绑在 Geneway「我的渠道」中由成员本人操作，由 Geneway 服务端完成；成员和浏览器不获得 `bot_token` 或其他凭据，凭据按 §6 存储并纳入备份与秘密扫描。
- 群聊：@ 机器人的消息只作为发送者本人渠道会话的入站，群内只回固定引导，私有结果只投递到发送者本人私聊；不存在群会话，也不把群历史注入任何成员的会话。

渠道会话：成员每个已绑定的渠道身份同一时刻只有一个活动渠道会话，默认对话 Agent 由成员在获准 Agent 中选择（未选择时使用管理员设定的默认 Agent，如小纬）。成员可在渠道中发送「新会话」或在 Web 操作，结束当前渠道会话并开启新的渠道会话，旧会话转为历史并可在 Web 查看；更换渠道默认 Agent 同样开启新的渠道会话。渠道中不能列出、绑定或切换到其他已有会话，也不能访问任何其他成员的会话。飞书与微信各自的渠道会话互相独立。其中“渠道内发「新会话」轮换”与“飞书、微信渠道会话各自独立”已由用户于 2026-10-15 确认，其余渠道会话细则由 P4 规划落实。P5 等主动通知的投递目标是成员的渠道身份，不随渠道会话轮换失效。

渠道模拟验收（用户 2026-10-15 决定）：飞书与微信的阶段验收不依赖真人操作，也不要求真实成员账号，改用模拟验收：

- 由脚本模拟至少两名成员的渠道操作。微信使用本地按 iLink 协议实现的模拟服务器（覆盖扫码登录、长轮询收消息、发送、重投、乱序、非主人发送者、上下文失效与拒发），Geneway 内置微信通道只通过可配置的协议地址连接它；该地址只允许在测试配置中指向本地，产品配置不能指向模拟服务器。飞书使用官方 SDK 的事件分发入口加模拟连接与客户端注入事件并捕获出站。
- 被测的是 Geneway 实际的渠道通道代码、产品服务、存储与 Web；不得用绕过渠道通道、直接调用产品服务的测试代替渠道旅程。Web 操作仍在真实浏览器中完成，模型与业务来源按既有阶段规则使用真实路由与 synthetic 数据。
- 验证记录、视频和说明明确标注“渠道为模拟验收”。模拟验收通过即满足 P4 及 J7、J12、AC-16、AC-17、AC-24 的渠道验收；真实飞书/微信账号上的联调是非阻塞的后续可选项，用户提出时再做，不阻塞 P4、P6、P7 或全量完成。

渠道身份可靠关联产品成员、员工与会话/工作。至少在飞书和微信通道（按上述模拟验收）完成交办、反馈和补充，并能在 Web 找到同一工作继续；从 Web 提交的获准后续回复也能投递到已绑定渠道。复杂配置或批准可以引导到经过认证的 Web 页面，但纯通知机器人不算完整渠道交互。

用外部消息标识与工作映射处理重投、回声和乱序，不能以相同文字或“最近一条”去重。未关联身份不能操作私有工作；群聊输出要检查接收范围，不能把私有结果因渠道绑定直接发给整群。回复失败显示待发送/失败，不伪称已送达，不重复执行原业务以重发消息。

尚未交付的内容在每次实际发送或重试前，复核当前接收者范围以及相关数据的有效共享/外发权限，不仅复用生成结果时的授权。共享撤销、接收者失权或无法确认可发送范围时，不发送受影响内容，明确待处理原因；已交付内容按既定历史与保留规则处理，不承诺远端撤回，也不推导出所有历史产出一律删除。P4 首次验证这一交接点，P5 自动通知复用同一语义。

成员被停用、解绑渠道身份或渠道账号失效后，该渠道身份的入站立即不再受理，待发送内容不再投递，并在 Web 明确显示原因；重新绑定得到新的渠道身份与新的渠道会话，不恢复他人或旧身份的访问。微信当前只承诺私聊；iLink 主动发送依赖该成员近期发来的消息上下文，平台拒发或结果未知时按“失败/待核对”如实显示，不以反复发送心跳或重试规避平台规则，P5 自动通知到微信同样适用。

Web 支持桌面与手机完成关键交办、补充、来源查看、停止与必要批准；不要求独立原生手机应用。附件/结果链接必须保持归属与访问检查。阶段计划确定要支持的文件类型和渠道能力差异，不声明任意文件或三个渠道完全同形。

### 5.5 定时、事件与较长任务

用户可配置规则的目标、执行员工、授权主体、时间或事件条件、结果接收者、启停和预算。规则属于创建它的成员，默认结果接收者限于该成员本人的 Web 与已绑定渠道；发送给其他成员或群聊须符合 §5.3 的明确共享与 §5.4 的接收范围检查。至少一种带明确时区的定时规则，以及一种真实来源事件规则，能在用户不持续聊天的情况下触发有界工作并反馈结果。

采用经过验证的原生能力或满足要求的成熟触发组件，产品只维护必要规则、发生标识与工作关联，不另写 Agent 循环。等待时间由规则/事件管理，不通过无休止调用模型模拟常驻员工。

区分消息重投、工作重复继续和业务动作重复三类身份。定时规则定义本次发生的标识、修改生效时间、重叠执行和重启漏触发处理；事件定义验证来源、稳定标识和重投语义。补跑默认不暗中扩大执行次数或副作用；具体策略由 P5 计划明确并在产品中可见。

规则禁用、成员失权或连接撤销后，即使已存在回调或候选记录，接受工作和实际派发仍复核当前状态。较长任务跨等待和重启可找到目标、已知结果与下一步，按明确策略继续或请求人工处理；不承诺任意崩溃点透明续跑。

P5 先交付真实读取、分析和通知；业务写入由 P6 增加动作级控制。具备调度功能不表示已经允许自动写入。停止本次运行、停用未来规则和撤销写许可的区别按 §4.2 落实。

- 承载位置：在 `mes-api` 内以上述唯一实现库挂载 Streamable HTTP MCP 端点，标注 `@ProductModule('mes.tpm')`（缺少标注会跳过模块授权检查）。每个工具只经 MES HTTP 路由（进程内路由注入）执行，不调用私有服务、不直连数据库（Kivo `AGENTS.md` 的 Agent 规则）。Kivo 现有 `JwtAuthGuard` 只认人类会话令牌，因此须增加内部机器主体：MCP 端点校验 OAuth 令牌（受众、范围、机器账号与密钥状态）后，在路由注入时携带只在进程内有效、外部不可伪造的机器主体；`JwtAuthGuard`、`PermissionGuard` 识别该主体并为其生成与人类用户同形的权限与组织数据范围（账号类型不得为终端），使权限、`@ProductModule` 与组织资源范围检查照常生效。外部请求直接用 OAuth 令牌访问业务路由、或用人类会话令牌访问 MCP 端点，均被拒。只包装已有稳定 API，不提供 PLC、设备控制、配置或报警处置类工具。若 P4-K0 探针证明在产品 API 内挂载不可行，须重规划，不得改为独立进程转发令牌。机器账号与授权服务器同样只实现一套，供 `mes-api` 与 `fms-api` 共用（具体落在 Kivo 共享包还是平台服务，由 P4-K0 规划）。
- 协议：MCP 规范 2026-07-28 版（用户所说“mcp 2”按此理解）。Kivo 端用 `@modelcontextprotocol/server` 2.x，Geneway 端用 `@modelcontextprotocol/client` 2.x，开工时取 npm `latest`（2026-10-15 为 2.3.1）并精确锁定。SDK 2.3.1 默认仍协商旧版协议，两端须显式只启用 2026-07-28：用 `server/discover` 而非 initialize，每个请求携带 `MCP-Protocol-Version`，Streamable HTTP 只用单一 POST 端点并携带 `Mcp-Method`/`Mcp-Name` 头；该端点拒绝旧版握手，并校验 `Origin`。端点与 `mes-api` 共用监听地址：测试实例只监听本机，生产环境的暴露范围由部署层（如反向代理按路径限制）控制，在 P7 确定。
- 鉴权（用户 2026-10-15 决定按长期更优方案）：遵循 MCP 规范的授权部分，不使用 Kivo 人类会话令牌。Kivo 作为授权服务器（显式 `issuer`），其元数据含 `token_endpoint_auth_methods_supported`（含 `private_key_jwt`）与 `token_endpoint_auth_signing_alg_values_supported`；MCP 端点发布受保护资源元数据（RFC 9728，well-known 路径与 `mes-api` 全局前缀和反向代理的配合在 P4-K0 确定）。机器客户端按 MCP 官方授权扩展 `io.modelcontextprotocol/oauth-client-credentials`（当前为草案；开工时锁定 ext-auth 仓库提交，草案有破坏性变更时按依赖变化重新评估）取得访问令牌，只采用 client credentials 授权加私钥签名 JWT 断言（RFC 7523，客户端身份由断言 `sub` 表达）；不实现授权码、PKCE、动态客户端注册、刷新令牌与共享口令。授权服务器校验断言的 `aud`、`exp`、`iat`、签名算法并拒绝重复的 `jti`；License 受限模式下不签发令牌。令牌以资源指示（RFC 8707）绑定 Kivo MCP 资源、短时有效、带与权限对应的范围；MCP 端点每个请求复核机器账号与密钥状态，不只依赖令牌过期，401 携带 `WWW-Authenticate` 与资源元数据地址，范围不足返回 `insufficient_scope`。Geneway 使用 SDK 2.x 自带的私钥 JWT 认证提供者（2.3.1 已导出），服务端秘密存储只保存机器账号私钥，Kivo 只保存公钥，支持轮换与吊销；令牌失效时重新获取或明确显示连接不可用，令牌与私钥不进入模型、浏览器、MCP 或产品日志。
- 机器账号：Kivo 新增独立的机器账号主体类型与加载器（不复用供内部 `mes-worker` 使用的 `runtime_worker_instance` 机器身份）：名称、命名空间、组织资源范围、角色/权限、公钥凭据、启用状态与审计；以受权限保护的管理 API 完成创建、停用和密钥轮换（页面可选），不能只能手改数据库。写入时控制器为机器账号生成主体与写入断言，断言中的设备与组织由服务端从目标设备解析；写入策略逐个动作显式允许机器执行：Geneway TPM 账号只开放 P6 的维修单创建；另按用户本轮确认，专属 FMS 机器账号可为原制造方法快照迁移执行锁定，保持原权限、dry-run、人工确认、幂等与机器审计，仅在本地 synthetic FMS 实例验证。Geneway TPM 账号不授该 FMS 权限，锁定写工具不进入模型列表；事务内复核机器账号启用状态与对应权限，保证批准后、派发前撤权仍然生效；审计与数据库写入上下文记为机器操作者。每个 Geneway 连接对应一个 Kivo 实例和一个机器账号，只授 synthetic 组织范围和所需最小权限：读 `tpm.repair.read`、`tpm.maintenance.read`、`tpm.inspection.read`、`tpm.plan.read`、`devices.device.read`，P6 另加 `mes.monitor.read` 与 `tpm.repair.report`；不授管理员角色及派工、验收、职责分离豁免等权限。
- 工具暴露：Geneway 插件内固定工具名及输入/输出 schema 指纹的允许清单，决定哪些只读工具可以暴露给模型；写工具只供 Geneway 确定性执行器在批准后调用，从不进入模型工具列表。`server/discover` 返回的未知、新增或 schema 不符的工具不暴露并按失败处理；服务端的只读等注解按规范属不可信提示，不作为授权依据。工具结果使用结构化输出并带来源时间，Geneway 校验结构，不因其中文字扩大权限（§6）。
- 成员隔离由 Geneway 负责，Kivo 侧只看到机器账号。Geneway 发往 Kivo 的请求携带 `x-trace-id`（Kivo 写入审计、outbox 与 webhook 的 `traceId`），写入另以 Geneway 指定的单号作为业务身份，用于双向追溯。
- 工作位置：Kivo 改动在 gewu-office 上由本地仓库独立克隆出的工作目录中进行，分支基于 `deploy/dongguan-airui`；不修改正在使用的 `~/.codex/worktrees/bd52/kivo`（其中有他人未提交改动），不对共享仓库执行 fetch、prune 或分支改写。改动须通过 Kivo 自身的类型检查与相关测试；提交只在该分支本地进行，推送或合入须另行授权。工作目录路径、分支和端口由 P4-K0 记录。
- 测试实例：由该工作目录启动一个或多个独立实例，各自使用独立的 MES 数据库、Redis 与端口（启动前核对 `DATABASE_URL` 与 Redis 不指向他人开发库），只监听本机；synthetic 组织、设备、账号与 TPM 记录，不使用东莞爱瑞或其他现场的真实数据。前置条件由 P4-K0 逐项落实：开发模式下的测试 License（含 `mes.tpm`，P6 加 `mes.monitor`）、独立 `JWT_SECRET`、通知主密钥与 webhook 地址策略、`mes-worker` 运行身份；P6 若使用 Hive 来源另需 Hive 外部 API 配置。Kivo 单号在实例内全局唯一，J4 的“相同编号”须用两个独立实例。

**事件来源（P5-K1）：**默认使用 Kivo 通知模块 `generic_json` webhook 订阅 TPM 业务事件（维修/保养/点检的状态、执行人、负责人等字段变化）；设备报警事件留待 P6 评估。Geneway 接收端校验 `webhook-id`、`webhook-timestamp`、`webhook-signature`（`whsec_` 密钥去掉前缀后按 base64 解码，`v1` HMAC-SHA256，覆盖“投递标识.时间戳.原始请求体”），用时间戳容差防重放、常量时间比较签名，以投递标识去重，先持久受理并在 10 秒内返回 2xx，再经 MCP 回读当前状态后派发工作，不以事件正文作为业务事实。Kivo 的 webhook 不保证送达（超时或 5xx 记为结果未知且不自动重试），因此 P5-K1 须定义经 MCP 定期对账的补偿方式；Geneway 自身写入引起的事件按 `traceId` 识别为回声。Kivo 投递地址策略只在测试配置中允许本机地址。不用 MCP 通知代替持久事件。

**关联分析（P6）：**两类真实来源为 Kivo TPM 记录与 Kivo 设备监控（设备当前状态与报警事实，依赖 Kivo 与 Hive 的设备绑定；缺少绑定时 Kivo 返回来源完整性未证明），以 Kivo 设备标识映射；是否需要 Hive 测试实例由 P6 重规划探针确定。无映射、多映射、来源过期或不完整要明确说明，不能猜设备或补齐演示字段；不继承旧 Geneway 专用令牌。

有限真实写动作是全量必达项。用户已决定（2026-10-15）采用：在 synthetic 设备上创建一张 Kivo 维修单（`POST mes/tpm/repairs`，仅传设备、原因与描述，不传指派人；单号由 Geneway 生成，带 `GW-` 前缀以免与 Kivo 自动单号冲突；按 `GET mes/tpm/repairs/:orderNo` 回读），由机器账号经 MCP 写工具执行。Kivo 当前创建维修单没有幂等回放、单号重复返回 HTTP 500；P6 在 Kivo 侧补上按单号幂等：只有已有单据由同一机器账号创建、在调用者读取范围内且内容（设备、原因、描述、来源）一致时，才返回该单当前状态并标记为回放（注明可能已流转）；其他情况一律返回 409 且不返回已有单据内容；并发请求撞上唯一约束时走同一判定，不再返回 500。补上之前或结果仍未知时（错误、超时、连接中断），先按单号回读并核对设备与原因；回读为 404 时多半是未写入或事务尚未提交，延迟后再回读，仍为 404 时用同一单号重提或转人工确认，不换单号盲目重发。P6 重规划按 Kivo 写操作惯例评估是否需要预览与确认分离。扩大对象范围或改变写动作仍属 §2.5 的用户决定；不把造一个仅存在于 Geneway 的临时文本视为上游真实写入。

默认采用人工核对动作预览后批准：服务端确定目标、变更内容和必要前置条件，批准绑定具体内容，拒绝/过期/撤权后不执行；执行前再次核对。自动规则默认最多生成待批准动作，无人确认写入不是本合同的默认权限。

实际写入使用上游可用的业务幂等能力或必要的动作身份，并回读真实系统结果。提交重试、渠道重投、子任务恢复不产生未识别的重复效果。超时但可能已经生效时先查询或人工确认，不盲目重发，也不让一次未知结果永久锁死无关业务。不承诺通用 exactly-once。

### 5.7 模型、运行反馈与交付

员工可配置模型/连接路由与支持的参数；最终验证至少两条不同提供方或兼容接入的真实模型路由，不能只有下拉框或模拟提供方。具体路由由合法账号及当前能力决定，不在合同预填不可用模型。切换不得丢失工作归属或突破允许的数据接收方；不可用路径明确反馈。

显示实际可得的调用量、耗时、失败、任务进展和预算信息；价格或用量未知时标未知，不编造费用。模型失败、预算用尽、渠道发送失败有明确停止/恢复入口，不隐式换到未经允许的提供方。

基础凭据保护和外发检查从 P1 生效；正式多人入口前落实成员认证、工作/知识/附件访问与服务端管理入口限制。P7 提供实际运行过的安装、启动、停止、配置、升级回退与备份恢复说明，以及依赖版本和故障定位入口。

## 6. 数据、外部系统与权限边界

原生部署配置拥有插件装配；产品数据拥有成员、员工、绑定、工作、知识范围、渠道关联和规则；凭据内容在服务端秘密存储，产品只持引用。需要页面编辑时写同一产品事实源，不保留独立可改的 YAML/数据库竞争副本。

业务系统拥有当前真实业务状态；历史观察是“当时读到什么”，不成为另一个 ERP。任务计划、协作关系、触发和动作记录只保存当前能力所需事实，不复制完整运行检查点。

合同修订本身不授权访问真实模型、飞书/微信、业务系统或生产数据。Kivo 侧 MCP、机器账号及其必需改动已获用户授权，只限 §5.6 写明的范围。从 dsh-im 复用的代码只引入 iLink 协议与扫码所需部分，不引入 AI Office Connector、语音转写、主动投递 HTTP 等额外外发或管理入口；微信凭据与长轮询状态纳入 §4.3 备份恢复与秘密扫描范围，恢复后已解绑的渠道身份不得重新生效。进入各阶段时使用明确的环境与凭据引用，不从旧项目扫描或挪用秘密。本轮用户明确指定 `~/.paseo/config.json` 中的 ZenMux API key 可供 Geneway 使用；只定点提取该凭据到 Geneway 服务端受限秘密存储，不读取其他项目凭据，不输出或提交密钥。消息发送、业务写入、跨仓库 API 建设、部署与发布分别核实范围；完成代码不推导出外部操作权。

缺少既有可用 API 时，将窄接口建设列为明确依赖及单独授权的工作，不能在修改 Geneway 时顺带改变其他生产项目。接口缺失只阻塞依赖它的任务，但对应目标仍是全量未完成，不自动降级为 fixture 验收。

使用真实数据前检查选定装配中的模型输入、附加会话日志、遥测、反馈、附件和其他启用的外发路径，关闭不必要导出。检查实际发送内容与接收方，不只看域名或总开关。业务材料和检索内容不可信，不能因其中的文字扩大工具权限、改变发送对象或获取秘密。

每条旅程使用同一候选中的关联对象和明确数据模式完整驱动；不能拼接多个不兼容版本或不同来源的局部成功。J10 不能替代各自权限、撤销、重复和失败边界测试。

## 8. 阶段计划的产物与验收组织

总合同固定目标与硬边界；阶段计划选择具体实现；验证记录保存真实结果。三者不复制成三套完整需求正文。

阶段计划包含本阶段所有必达任务及受阻项，而不是只描述最容易先做的切片。按 §2 完成团队规划后，可以逐项实施就绪任务，不把“接口未知”变成无限扩建框架的理由。对真实外部依赖保留明确的取得条件、责任和影响。

当新增能力使跨能力风险首次可达，本阶段即在已有旅程中验证相应交接点的归属、权限、撤销、取消和恢复语义；P7 汇总完整组合，不承担这些边界的首次验证。P3 关注知识交接和协作撤销，P4 关注结果生成后待发送/重试的权限变化，P5 复用到自动触发，P6 覆盖批准后实际派发前的权限与目标变化。只检查本阶段实际出现的交接点，不提前实施后续能力、不穷举所有组合或建设新验收平台。

实现任务可命名为 P1-T1 等，在该阶段计划中描述拟建或实际文件、验证命令和输出；编号本身不授予权限。小型安装/代码探针也必须属于已规划任务。探针结束时交付可运行的实际产品路径，允许起初用少量实验代码核验接口，不以第一次代码或提交次数设置额外限制。

阶段验证记录给出实际执行过的命令、普通入口、候选版本、相关对象、真实/受控数据模式、结果和未运行项。仅构建通过、HTTP 200、工具注册或截图不等于产品旅程通过。文档检查不等于能力验证，planner 同意不等于用户接受或正式认证。

## 12. 全量完成与交接

宣布全量完成必须同时满足：G1–G9 的必达行为、P1–P7 实际阶段交付、J1–J12 适用完整旅程、AC-01–AC-25 均有对应有效结果；真实模型/来源/写入缺口已解决，渠道按 §5.4 模拟验收通过；不存在会使已交付行为不安全或失真的已知阻断；安装、运行和恢复入口可复现。

任何未跑、失败、未知或仅受控替代的真实要求，保留为未完成；可以说明已经完成哪些工程和阶段，不能把必达能力移到“以后版本”后宣布全量通过。产品验收与实际生产部署、客户接受、正式发布是不同结论，不互相推导。

每个大阶段（包括因本版修订而重开的 P4）都重复先规划后实施的顺序：先由 planner team 原位更新该阶段详细计划，完成独立过度设计审查，再进行其升级、探针和代码实施。本次合同修订不算 P4 详细重规划已完成；v4.4 修订同样不算 P4-K0、P5-K1 及 P6 的 Kivo 重规划已完成。

只在当前目标内修复实现缺口和回归，不扩成无关平台。改变全量目标需用户明确决定，改变工程方案在相应阶段重规划；本合同仍坚持全新建设、原生底座、产品语义清楚和最少重复维护责任。

澄清及修订事实见 [澄清与修订记录](clarification-notes.md)，其历史内容不新增当前义务；各阶段计划与验证记录在实际形成后关联，不预先列作已存在交付。
